# API Review

Review only callable interfaces and their cross-file caller obligations. Return draft findings; do not edit files or post comments.

## Review

1. Read complete changed files, sibling APIs, tests, local conventions, and enough representative call sites to enumerate every materially distinct caller pattern. Expand to every reachable call site only when the changed contract is broad or a pattern, ownership decision, or consequence remains unresolved. When the selected axis or reachable evidence concerns a caller-visible async value, error protocol, fallback, or lifecycle obligation, follow a representative value through the first stateful cache, state, or render consumer. If fallback, retry, or refetch is part of that obligation, trace the observable failure → fallback → recovery transition rather than stopping at the producer.
2. Write the smallest ideal call site before judging the actual one. Compare setup/ordering/cleanup duties, required options, conversions, and error handling.
3. For each materially distinct caller pattern, write a compact caller-obligation ledger and cite representative call sites: `caller goal | caller-owned policy | module-owned mechanics | leaked implementation knowledge | builtin alternative`. Group equivalent call sites instead of repeating the same obligations. Caller-owned policy is a product/domain decision the caller genuinely makes or observes. Module-owned mechanics include repeatable setup, ordering, cleanup, lifecycle, internal IDs, wrappers, callback wiring, provider configuration, conversions, and error protocol that the module can own completely.
4. For each changed or axis-relevant injected callback, configuration value, or wrapper, trace where each materially distinct caller pattern obtains it and whether the caller uses it independently of forwarding it. Different implementations do not by themselves make the choice caller-owned. Separate genuinely dynamic product policy from stable caller context that the callee could derive; when stable caller context fully determines the mechanics, compare the current API with a context-specific zero-configuration call or an honest discriminated input.
5. Check whether the interface is shaped around an implementation or first caller, whether a small interface hides meaningful behavior/invariants, and whether a custom class/manager/adapter could be a plain function, Promise, iterable, `AbortSignal`, discriminated union, or object.
6. Judge module depth by caller leverage: prefer an interface that lets callers express domain intent while hiding implementation wiring, invariant enforcement, sequencing, and lifecycle. Do not optimize for fewer parameters when the removed concept is a legitimate caller decision.
7. When reachable evidence raises a module-depth, ownership, trust-boundary, or abstraction-timing question, read [Practical Design Foundations](../code/references/design-foundations.md). Apply the evidence-supported questions, not the reference as a checklist, and name the observed caller burden before design terminology.
8. Keep the API in one vocabulary. When positive composition evidence includes a caller-obligation or seam question, read [Feature Composition and Mechanism Primitives](../code/references/composition.md); report caller burden here and defer a distinct mechanism-placement or dependency-direction question to `$sb:architecture-review`.
9. Do not generalize a pass-through or add option sprawl without a concrete caller or independent mechanism. A one-caller primitive remains valid when its behavior/invariants/test surface are real.

## Output

Start with `axis | disposition | required artifacts complete/missing`. Order candidate findings by caller pain and provisional severity; Main owns final disposition. Include the grouped caller-obligation ledger with representative call sites and the affected scope, exact location, reachable call-site evidence, current and ideal call-site sketches, material consequence, strongest checked disconfirming evidence, smallest interface change, verification, migration notes, and a review-comment draft. Defer a distinct ownership or dependency-direction question to `$sb:architecture-review`, intent-only names to `$sb:intent-review`, and general correctness to `$sb:code-review`. If no actionable finding remains, still include the grouped ledger, the current-versus-ideal comparison or why they are materially identical, and the strongest counterevidence. Explain which domain operations callers can express, which implementation details the module hides, and why callers have no unnecessary setup, ordering, conversion, or cleanup duties.
